### S1-05: Build retrieval pipeline step (hybrid search)

| Field | Value |
|---|---|
| **Owner** | Nancy + Atharva |
| **QA Buddy** | Nishka |
| **Estimate** | 3 person-days |
| **Sprint** | Sprint 1 |
| **Days** | May 3--5 |
| **Bucket** | Data work + AI engineering |
| **Dependencies** | S1-02 (KB articles indexed with embeddings), S1-04 (LLM Gateway for embed()) |

**User value**: The copilot retrieves the most relevant KB articles for any incoming ticket, combining semantic understanding (vector search) with keyword matching, so support agents get accurate reference material.

**Acceptance criteria**:

- [ ] **Given** a ticket text string, **when** `retrieve(ticketText, K)` is called, **then** it returns an array of up to K KB articles, each with fields: `kb_id`, `title`, `content`, `relevance_score`.
- [ ] **Given** a ticket text, **when** the retrieval step runs, **then** the ticket text is embedded using `LLMProvider.embed()` via Vertex AI `text-embedding-005`, producing a 768-dimensional query vector.
- [ ] **Given** the query vector is produced, **when** the Elasticsearch query executes, **then** it combines a kNN vector search on the `kb_vectors` index with a BM25 keyword match on the `kb_articles` index.
- [ ] **Given** both kNN and BM25 results are returned, **when** results are merged, **then** Reciprocal Rank Fusion (RRF) is applied to produce a single ranked list with unified relevance scores.
- [ ] **Given** no explicit K parameter is passed, **when** retrieve is called, **then** it defaults to K=3; **given** K=5 is passed, **then** it returns up to 5 results.
- [ ] **Given** a ticket about "SSO login fails after password reset" (matches KB-001), **when** the unit test runs retrieve against the indexed dataset, **then** KB-001 appears in the top-3 results.
- [ ] **Given** a ticket with no relevant KB match (e.g., "How do I change my laptop wallpaper?"), **when** retrieve runs, **then** all returned articles have `relevance_score` below a configurable threshold (default 0.3).

### S1-06: Build reason pipeline step

| Field | Value |
|---|---|
| **Owner** | Atharva |
| **QA Buddy** | Amit |
| **Estimate** | 2 person-days |
| **Sprint** | Sprint 1 |
| **Days** | May 5--6 |

| **Dependencies** | S1-03 (classify output), S1-05 (retrieve output) |

**User value**: The copilot reasons about the best course of action for each ticket -- reply, ask for more info, or escalate -- so support agents get an actionable recommendation rather than raw data.

**Acceptance criteria**:

- [ ] **Given** a ticket object, an array of retrieved KB articles, and the escalation rules JSON, **when** `reason(ticket, kbArticles, escalationRules)` is called, **then** it returns structured JSON: `{ action, reasoning, escalation_team?, required_context?, confidence }`.
- [ ] **Given** any ticket, **when** the reason step returns, **then** `action` is exactly one of: `Reply`, `Ask`, `Escalate`; and `confidence` is a float between 0.0 and 1.0.
- [ ] **Given** the reason function runs, **when** the prompt is inspected, **then** it uses a chain-of-thought prompting pattern loaded from the versioned template file `prompts/reason.txt`.
- [ ] **Given** a ticket that matches an escalation rule (e.g., a critical billing issue mentioning "data breach"), **when** reason runs, **then** it returns `action: "Escalate"` with the correct `escalation_team` and `required_context` fields populated per the matching rule.
- [ ] **Given** a ticket with a clear KB match that contains a resolution (e.g., password reset steps in KB-001), **when** reason runs, **then** it returns `action: "Reply"` with `reasoning` referencing the KB article.
- [ ] **Given** a ticket with insufficient information (e.g., "It's not working" with no context), **when** reason runs, **then** it returns `action: "Ask"` with `reasoning` explaining what additional information is needed.
- [ ] **Given** 3 test tickets covering all 3 action types (Reply, Ask, Escalate), **when** the unit test suite runs, **then** each returns the expected action type.
